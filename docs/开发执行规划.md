# 二、铁律 0：单写者原则（最重要的一条）

> **同一时刻只允许一个 AI 修改这个仓库。**

原因：你的 ChatGPT 桌面端的 Codex **此刻正在这个目录里工作**。证据：

- 11:41 我读到 `login-form.tsx` 仍有 `useEffect` 里 setState 的 lint 错误；11:42 该文件已被改成服务端读 `searchParams`，lint 错误消失。
- 11:42:37 `docs/MVP-TASKS.md` 被更新为「当前进度：Sprint 2（项目管理）——Sprint 0、Sprint 1 已完成 ✅」。

两个 AI 同时写同一份代码库，会产生：文件互相覆盖、任务清单状态错乱、迁移文件冲突、git 历史无法解读。**代价远大于并行带来的速度收益。**

因此本文第三节的分工不是"能者多劳"，而是"避免撞车"。

# 四、总体路线（阶段化）

```text
阶段 A  收口 Sprint 2        ← 当前所在位置
阶段 B  Sprint 3 + Sprint 4   问卷 / 人员关系（Excel 双导入）
阶段 C  Sprint 5 + Sprint 6   评价端单人 / 矩阵
阶段 D  Sprint 7              评分引擎（系统核心，测试先行）
阶段 E  Sprint 8 + Sprint 9   进度冻结 / Excel 导出
阶段 F  MVP 真实验收         5 被评人 × 20 评价人 × 30 题
阶段 G  V1 立项               报告 / PDF / 多维表格 / 拖拽编辑器
```

### 阶段 A：收口 Sprint 2（项目管理）

Codex 已在进行中。**验收清单**（缺一项就不算完成）：

- [ ] `Project` / `ProjectAdmin` / `ProjectScale` 模型 + migration 已生成
- [ ] 状态机 DRAFT → PUBLISHED → ACTIVE → CLOSED → FROZEN → ARCHIVED 流转正确
- [ ] `unfreeze` 仅系统管理员可调用（HR 项目管理员必须 403）
- [ ] 关系权重 ≠ 100% 时**无法发布**（这是 PRD 第 33 节的硬校验，必须有测试）
- [ ] **`requireProjectAdmin(projectId)` 已回填**（Sprint 1 顺延项，本 Sprint 必须还）
- [ ] HR 只能看到自己管理的项目（跨项目访问返回 403，需服务端测试）
- [ ] 四件套全绿 + MVP-TASKS 勾选 + 一个独立 commit

### 阶段 B：Sprint 3 + 4（最容易埋雷）

问卷 Excel 导入、人员关系 Excel 导入是整个 MVP 最容易出问题的地方。硬要求：

1. **Preview / Commit 两阶段**，Commit 必须在数据库事务内，失败整批回滚。
2. 导入校验逻辑必须是**纯函数**放 `modules/excel`，用单元测试覆盖 PRD 第 18 节的全部错误类型（工号为空、姓名空、工号姓名冲突、重复关系、同一评价人对同一被评人两个关系、非法关系类型）。
3. 性能门槛：860 行量级 Preview **秒级返回**，必须有量级测试（不要等真实数据才发现卡）。
4. 自评自动生成（`selfReviewEnabled`）要写集成测试。

### 阶段 C：Sprint 5 + 6（评价端）

顺序不能反：**先单人，跑通数据逻辑，再做矩阵**。矩阵与单人**必须共享同一份 DraftAnswer**（`unique(taskId, questionId)`），这是最容易做错的一点 —— 一定要有"矩阵填一半 → 切单人 → 数据完整"的自动化测试。

草稿隐私（AGENTS 铁律 4）在 Sprint 5 就要有**反向测试**：所有 HR 端接口都不能返回 DraftAnswer 内容。

### 阶段 D：Sprint 7（评分引擎，最高风险）

- **测试先行**，覆盖技术文档第 59 节全部场景，覆盖率 ≥ 90%。
- 全链路用 Decimal，中间结果**永不舍入**。
- 独立 PR、独立会话，**这一 Sprint 不要同时改任何 UI**。
- 验收硬标准：PRD 第 31/32 节的示例数值（3.5/4.0/4.5 → 4.00；40:30 权重归一化）逐条对得上。

### 阶段 E：Sprint 8 + 9（结果与导出）

- 冻结 = 计算 + 落 `ResultSnapshot`，**之后报告只读快照**。要有一个测试证明"冻结后修改业务表不影响结果"。
- 允许未 100% 完成冻结，但必须展示完整性警告（PRD 第 36 节）。
- Excel 6 个 Sheet，字段名固定（便于 Power Query）。

### 阶段 F：MVP 真实验收

按 PRD 第 47 节 + 技术文档第 77 节，建议真实小范围：**5 名被评人 × 20 名评价人 × 30 量表题 + 3 开放题**，全程不手工改库。

# 五、每个 Sprint 的固定作业流

这是把"AI 帮你开发"从碰运气变成可重复流程的关键。

```text
① 开新会话，只做这一个 Sprint
      ↓
② 让 AI 先出计划，不写码
   （改动清单 + 数据模型 + API 清单 + 测试清单）
      ↓
③ 人工确认计划（尤其数据模型和口径）
      ↓
④ 测试先行 → 实现（一个任务一个闭环）
      ↓
⑤ 四件套验证：lint + typecheck + test + e2e
      ↓
⑥ 勾选 MVP-TASKS → git commit（一个 Sprint 一个提交）
```

**纪律**：③ 之前不许写代码；⑤ 不绿不算完成；⑥ 必须提交。

# 七、风险清单（按优先级，含"现在就要处理"）

### 🔴 P0-1：飞书工号（employeeNo）可能取不到 —— 整个身份方案的地基

PRD 第 22 节的技术方案是：`飞书员工工号 = 项目导入工号`。

这个方案成立的前提是**飞书侧已维护员工工号**。但飞书的"工号"字段是企业**选填**信息，很多公司不维护；且自建应用读取 `employee_no` 还需要额外的通讯录权限。

**万一飞书侧工号为空，整个登录与任务匹配方案失效**（届时只能退回手机号/邮箱匹配，改造成本高）。

> **必须现在就验证，不要等到 MVP 做完。** 验证方式：用已有的飞书工作账号凭据查一次当前用户的 `employee_no` / `job_number` 字段是否非空。这一步 5 分钟，能决定 PRD 第 22 节是否需要改口径。

### 🔴 P0-2：全部工作尚未提交 git

`git log` 只有一条 `Initial commit from Create Next App`。Sprint 0 与 Sprint 1 的**全部成果都还是未跟踪文件**。

同时 `.git/index.lock`（0 字节，11:41 残留）存在，会导致 git 写操作报错。

**风险**：Codex 任何一次误操作 → 一天的成果归零。**建议今天先提交两个 commit**（`feat: sprint0 skeleton` / `feat: sprint1 auth`）。

### 🟠 P1-1：飞书 OAuth 端点版本混用

`modules/feishu/auth.ts` 目前是：

- 授权：`authen/v1/authorize`（旧版，走 `app_id` 参数，`open.feishu.cn`）
- 换 token：`authen/v2/oauth/token`（新版，走 `client_id/client_secret`）
- 取用户：`authen/v1/user_info`

v2 的 token 端点通常需要配套 v2 的授权入口（`accounts.feishu.cn/.../authen/v1/authorize`，`client_id` + `response_type=code`）。**新旧混用极可能拿不到 code 或换不到 token。**

**建议**：在 Sprint 3 之前安排一次 30 分钟的"飞书登真机联调 spike"，用真实 `FEISHU_APP_ID` 走通一次 PC 扫码登录，把端点组合钉死。不要拖到 MVP 验收。

### 🟠 P1-2：生产环境未对 `AUTH_MODE=mock` 做 fail-fast

`loginWithMock` 已在服务端校验 `AUTH_MODE !== "mock"` 就返回 404（很好）。但生产部署时若误配 `AUTH_MODE=mock`，等于**任意工号即可登录、并自动创建账号**。

**建议**：加启动断言 —— `NODE_ENV=production && AUTH_MODE=mock` 直接抛错拒绝启动，并加一条测试。

### 🟡 P2-1：`app/generated/prisma` 生成在 Next.js 路由根目录内

生成物位于 `app/generated/prisma`（已在 `.gitignore`）。Next.js 只会把 `page.tsx`/`route.ts` 等特名文件当路由，暂不出问题；但把生成物放进 `app/` 语义上别扭，也容易被 lint/构建扫描。

**建议**（非阻塞）：迁到 `lib/generated/prisma`，改 3 处（`prisma/schema.prisma` 的 output、`lib/db/prisma.ts`、`prisma/seed.ts` 的 import）。

### 🟡 P2-2：`vitest.config.ts` 的 ESM/CJS 警告

Vite 未来版本会默认 `configLoader: 'native'`，当前配置会失效。改 `.mts` 后缀或 `package.json` 加 `"type": "module"`（后者影响面太大，建议只改后缀）。
